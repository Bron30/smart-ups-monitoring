📖 Smart UPS User Manual

QR-Enabled Intelligent UPS Monitoring and Maintenance System

1. System Overview

The Smart UPS project demonstrates a DC power monitoring and load-management system using an ESP32, sensors, Firebase cloud storage and a QR-authenticated web dashboard.

System objectives:
  • Monitor battery voltage, current and temperature when suitable sensors are connected.
  • Display battery State of Charge (SoC) and overall UPS status.
  • Monitor current and power for individual DC load channels.
  • Support priority-based load shedding and recovery through suitable firmware and switching hardware.
  • Display system events and operating information.
  • Provide QR-based authenticated access to monitoring, maintenance and documentation pages.
Implementation status: The website and Firebase dashboard currently display configured database values. Do not treat those values as live sensor measurements or actual load-switch states until the ESP32, sensors and switching hardware are connected and verified.

2. System Architecture

DC Battery → Sensors → ESP32 → Wi-Fi → Firebase → QR-Authenticated Web Dashboard

Prototype scope:
  • The current project focuses on a low-voltage DC UPS prototype.
  • The ESP32 is intended to collect sensor readings and execute local control logic.
  • Firebase stores monitoring data for remote dashboard access.
  • The web dashboard displays telemetry, load channels, events and documentation.
A commercial UPS may contain a rectifier, battery bank, inverter, DC link and bypass circuitry. These commercial features must not be assumed to exist in this DC-only student prototype.

3. Parameters Monitored

  • Battery Voltage: DC voltage measured across the battery using a suitably rated voltage-sensing circuit.
  • Battery Current: Battery charge or discharge current measured using an appropriate current sensor.
  • Battery Temperature: Temperature measured by the installed temperature sensor.
  • Battery SoC: Estimated remaining battery charge, expressed as a percentage. Its accuracy depends on the estimation method, battery condition and measurement quality.
  • Total DC Load: Combined load power, calculated from measured values or supplied as configured demonstration data.
  • Individual Load Current: Current associated with each configured DC output channel.
  • UPS Status: A status such as Healthy, Warning or Fault, according to the implemented monitoring logic.
  • Operating Mode: An optional firmware-defined mode such as NORMAL, LOAD_SHEDDING, CHARGING, RECOVERY or FAULT.
  • Timestamp: The recorded time associated with a telemetry update or event.
A displayed value is only as reliable as its sensor, calibration, firmware and database update process. A blank operating mode means that a corresponding value may not have been configured in Firebase.

4. Per-Load Monitoring

The dashboard is configured for four demonstration DC load channels. Their labels and priority assignments should match the actual hardware and firmware configuration.

  • CH1 — Critical load: Intended for a critical demonstration load, such as a small networking or POS-type DC load. It is retained during ordinary SoC-based load shedding.
  • CH2 — Medium priority: Intended for a demonstration load such as emergency lighting.
  • CH3 — Medium priority: Intended for a DC motor or other demonstration load. Motor startup current must be considered when selecting the driver and current sensor.
  • CH4 — Non-critical load: Intended for a demonstration lamp and is the first channel scheduled for SoC-based shedding.

The Firebase channel records use the fields Name Current Power Relay

The Relay field in Firebase is a displayed data value. It does not prove that a physical relay or MOSFET channel has switched. Confirm switching at the hardware before describing the channel as physically ON or OFF.

5. Automatic Load-Shedding Logic

The proposed control strategy sheds lower-priority loads as battery SoC decreases. Separate shedding and restoration thresholds provide hysteresis to reduce repeated switching near a threshold.

  • SoC below 60%: Shed CH4.
  • SoC below 40%: Shed CH3 as well.
  • SoC below 25%: Shed CH2 as well.
  • CH1: Retain during ordinary SoC-based shedding.
  • Protection override: A serious electrical fault or battery-protection condition may require shutting down affected channels, including a normally critical channel.

Restoration thresholds

  • CH2 may be restored at SoC ≥ 35%.
  • CH3 may be restored at SoC ≥ 50%.
  • CH4 may be restored at SoC ≥ 70%.
These are the proposed project thresholds. Automatic shedding and recovery occur only when the corresponding ESP32 firmware and physical switching stage have been implemented and tested. The website alone does not perform hardware load shedding.

6. Operating the Digital Dashboard

  1. Scan the QR code assigned to the UPS.
  2. Open the URL encoded in the QR code.
  3. Enter an authorized Firebase Email/Password account.
  4. The gateway authenticates the account and checks the QR ID against the configured security record.
  5. If the QR record is active and the access log is written successfully, the gateway redirects to the requested page.
  6. Open the main dashboard to review the configured UPS overview.
  7. Open UPS Monitoring to view detailed telemetry, load channels and events.
  8. Open Maintenance to review the configured maintenance information.
  9. Open Documentation to access this manual and the troubleshooting guide.
Authentication reminder: Only authorized accounts should be used. Access requires both a successful sign-in and an active matching QR record.

7. Events and Maintenance

The event history can be used to record configured system activities, including initialization, load-state changes and protection events.

The Maintenance page can display service information such as the previous service date, next service date and maintenance notes when those fields are configured in Firebase.

Event history and maintenance dates should reflect actual recorded operations or clearly identified demonstration data. Do not assume that an event proves a physical load changed state unless the hardware state has been verified.

8. Network and Cloud Operation

  • The ESP32 is intended to perform local sensor monitoring and control.
  • Wi-Fi provides connectivity to Firebase when a network is available.
  • The website reads configured Firebase values for remote display.
  • Loss of Wi-Fi or Firebase connectivity should not disable essential local protection.
  • Local load-control decisions should not depend exclusively on cloud availability.
  • Database rules should restrict unauthorized access and prevent ordinary dashboard users from changing protected telemetry.
Local operation during network failure must be implemented and tested in the ESP32 firmware. A cloud dashboard by itself cannot guarantee offline monitoring or protection.

9. Safety Precautions

Important: This project is a low-voltage DC prototype. Never connect breadboard wiring, ESP32 GPIO pins or non-isolated prototype circuits directly to hazardous mains voltage.
  • Use a suitable Battery Management System (BMS), charger and battery protection for the selected battery chemistry and configuration.
  • Use compatible, properly matched cells and inspect them for damage.
  • Fit appropriate fuses close to the battery source and use wiring rated for the expected current.
  • Observe correct polarity and avoid short-circuiting battery terminals.
  • Do not exceed the ratings of the battery, sensors, switching devices, connectors or wiring.
  • Account for DC motor startup and stall current when choosing drivers and protection.
  • Disconnect the battery and other power sources before modifying the hardware.
  • Never bypass the BMS or other protective devices.
  • Use appropriate isolation and qualified personnel for any future mains-voltage integration.

10. Recommended Demonstration Sequence

  1. Inspect the low-voltage DC hardware, battery protection and wiring before applying power.
  2. Verify each sensor reading against a suitable reference instrument.
  3. Confirm that the dashboard displays the expected telemetry.
  4. Demonstrate the four configured load channels and verify physical switching if the hardware is installed.
  5. Test CH4 shedding at the configured threshold under controlled conditions.
  6. Test CH3 and CH2 shedding at their respective thresholds.
  7. Confirm CH1 remains enabled during ordinary SoC-based shedding, while protection logic can override normal priorities.
  8. Raise SoC or use a safe test procedure to demonstrate staged restoration.
  9. Verify that events correspond to actual state changes.
  10. Demonstrate QR authentication and denial when the QR record is revoked or invalid.
Do not deliberately over-discharge, overheat or short-circuit a lithium-ion battery to demonstrate protection. Use a safe test method and suitable test equipment.

11. Troubleshooting

Use the dedicated Troubleshooting Guide for common issues involving sensor readings, Firebase connectivity, authentication, dashboard updates and load-control behaviour.

Before troubleshooting:
  • Check the power supply and wiring.
  • Confirm that the relevant sensor and firmware are configured.
  • Verify that the expected Firebase path and field names exist.
  • Check browser developer-console errors if the dashboard fails to load.
  • Never weaken Firebase security rules merely to hide a permission error.
